# Deterministic Identifier Scheme

Canonical identity and identifier allocation for ArchiMate 3.2 Open Exchange XML
model files owned by this repository. The machine-readable parameters live in
`identity-config.json` next to this document; both files are normative for
fixtures under `docs/architecture/models/` and for the mutation engine under
`scripts/archimate/`.

## Why deterministic identifiers

Exchange XML identifiers are `xs:ID` values, so they must be unique, non-empty
NCNames. Raw UUID4 values satisfy uniqueness but are opaque, start with digits
or hyphens half the time (invalid NCNames), and change on every export, which
makes agent mutations non-idempotent and review diffs noisy. Deriving
identifiers from canonical identity instead makes re-application of the same
logical object reuse the same identifier, keeps review diffs limited to real
changes, and lets reviewers verify an identifier by recomputing it.

## Canonical identity

The canonical identity of an object is the UTF-8 string:

```
archimate:3.2|{kind}|{type}|{name}
```

- `{kind}` — `model`, `element`, `relationship`, `view`, `item`,
  `property_definition`, `diagram_node`, `diagram_connection`.
- `{type}` — the `xsi:type` value for elements, relationships, and views
  (for example `BusinessActor`, `Serving`, `Diagram`); `model` for the model
  root; `folder` for organization items; the property definition `type`
  attribute (for example `string`) for property definitions.
- `{name}` — the text of the object's first `name` element (or `label` for
  organization items). For diagram nodes, `{name}` is
  `{view identifier}:{elementRef}`; for diagram connections it is
  `{view identifier}:{relationshipRef}`.
- Names are Unicode-NFC normalized, outer whitespace trimmed, internal
  whitespace preserved, case-sensitive. Layer is not an identity input; two
  same-typed concepts with the same name in different layers are a collision
  and take the suffix rule below.

## Identifier derivation

```
identifier = {prefix}-{sha256(canonical_identity)[0:16]}
```

- SHA-256, lowercase hexadecimal, first 16 characters.
- Prefixes: `model`, `ea` (elements), `rel` (relationships), `view`,
  `item` (organization items), `prop` (property definitions), `node`
  (diagram nodes), `conn` (diagram connections).
- Result is a valid NCName (`^[A-Za-z][A-Za-z0-9._-]{0,63}$`): letter prefix,
  hyphen, then hex characters only.

Example: the element with `xsi:type="BusinessActor"` and name
`Claims Administrator`:

```
archimate:3.2|element|BusinessActor|Claims Administrator
  -> sha256 = a87d4730...
  -> identifier = ea-a87d473086132d9f
```

## Collision handling

Distinct objects that normalize to the same canonical identity (for example
two same-named elements of the same type in different layers) append `-2`,
`-3`, ... in stable document order: the first-declared object keeps the bare
identifier, later ones take `-{n}`. Re-applying the same logical object under
the same identity reuses the original identifier; the bare identifier is never
re-allocated to a different object within a model. A mutation that would
introduce a collision is reported rather than silently re-hashed.

## Preservation

Existing identifiers are never recomputed. The scheme governs allocation of
identifiers for new objects only; renames leave identifiers stable, which is
what keeps round-trips and re-applied mutations free of identifier churn.

## Verification

`canonical.xml` and every regression fixture in `regression/` carry
identifiers generated by this scheme. A reviewer can recompute any identifier
from the object's `xsi:type` and `name` using `identity-config.json`
parameters; the fixture manifest records the fixture-level expectations.
