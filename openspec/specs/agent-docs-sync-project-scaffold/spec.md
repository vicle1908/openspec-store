## Purpose

Define the project scaffold capability for docs-sync: initial documentation structure creation, template-based doc generation, and repository-specific documentation layout conventions.

## Requirements

### Requirement: CLAUDE.md project instructions

The system SHALL have a CLAUDE.md file with project-specific instructions for AI assistants.

#### Scenario: CLAUDE.md exists
- **WHEN** an AI assistant works in the agent-docs-sync directory
- **THEN** it SHALL find a CLAUDE.md at the repo root
- **AND** CLAUDE.md SHALL document the CLI commands (check, update, validate, sync, sync-all)
- **AND** CLAUDE.md SHALL document the pipeline architecture (detect → analyze → generate → validate → report)
- **AND** CLAUDE.md SHALL document the LLM configuration (OmniRoute gateway, model selection)
- **AND** CLAUDE.md SHALL reference tdt-meta CLAUDE.md for workspace-wide conventions

#### Scenario: CLAUDE.md does not duplicate workspace content
- **WHEN** CLAUDE.md is written
- **THEN** it SHALL NOT duplicate content from the workspace CLAUDE.md
- **AND** it SHALL focus on agent-docs-sync-specific guidance
- **AND** it SHALL reference workspace conventions via link or mention

### Requirement: AGENTS.md agent documentation

The system SHALL have an AGENTS.md file documenting agent patterns.

#### Scenario: AGENTS.md exists
- **WHEN** an AI assistant needs to understand agent-docs-sync's agent architecture
- **THEN** it SHALL find an AGENTS.md at the repo root
- **AND** AGENTS.md SHALL document the two agent types: doc_sync_agent and generation_agent
- **AND** AGENTS.md SHALL document the tool registry (10 tools with approval flags)
- **AND** AGENTS.md SHALL document the flavor system (check, generate, full_sync modes)
- **AND** AGENTS.md SHALL document the durable workflow path (SchedulerEngine integration)

#### Scenario: AGENTS.md references workspace patterns
- **WHEN** AGENTS.md is written
- **THEN** it SHALL reference the workspace AGENTS.md for cross-repo orchestration
- **AND** it SHALL reference agent-core's BaseAgent, ToolRegistry, and HookRegistry patterns

### Requirement: Clean git state

The system SHALL have a clean git working tree after setup.

#### Scenario: All files committed
- **WHEN** setup completes
- **THEN** `git status` SHALL show no modified files
- **AND** all 13 previously modified files SHALL be committed
- **AND** the commit message SHALL follow conventional commit format

#### Scenario: Code quality verified
- **WHEN** files are committed
- **THEN** `ruff check .` SHALL pass with no errors
- **AND** `ruff format .` SHALL produce no changes
- **AND** `mypy src/ --strict` SHALL pass (or known issues documented)

### Requirement: .gitignore updated

The system SHALL have appropriate .gitignore entries for tooling artifacts.

#### Scenario: gitnexus artifacts ignored
- **WHEN** .gitignore is updated
- **THEN** `.gitnexus/` SHALL be fully gitignored (entire directory is auto-generated)
- **AND** `.gitnexus/lbug` SHALL be gitignored (large binary database)
- **AND** `.gitnexus/parse-cache/` SHALL be gitignored
- **AND** `.gitnexus/parsedfile-cache/` SHALL be gitignored
- **AND** `.gitnexus/run.cjs` SHALL be gitignored (auto-refreshed)
- **AND** `.gitnexus/gitnexus.json` and `.gitnexus/meta.json` SHALL be gitignored (regenerated by analyze)

#### Scenario: graphify artifacts handling
- **WHEN** .gitignore is updated
- **THEN** `graphify-out/` SHALL be gitignored (auto-generated, regenerable via `graphify update .`)
- **AND** `graphify-out/cache/` SHALL be gitignored (AST cache, large number of files)
- **AND** `graphify-out/graph.json` SHALL be gitignored (regenerated by post-commit hook)

### Requirement: Post-commit hook installation

The system SHALL have git hooks that refresh code intelligence indexes after commits and branch switches.

#### Scenario: Graphify hooks installed via built-in command
- **WHEN** `graphify hook install` is run from agent-docs-sync root
- **THEN** it SHALL install a post-commit hook that calls `_rebuild_code()` for incremental AST rebuild
- **AND** it SHALL install a post-checkout hook that rebuilds on branch switches
- **AND** hooks SHALL use `nohup` + `disown` for non-blocking background execution
- **AND** hooks SHALL skip during rebase/merge/cherry-pick operations
- **AND** `graphify hook status` SHALL report both hooks as "installed"

#### Scenario: GitNexus refresh appended to graphify hook
- **WHEN** the graphify post-commit hook is installed
- **THEN** a gitnexus refresh section SHALL be appended between markers in the same post-commit hook
- **AND** it SHALL run `npx gitnexus analyze` in background after graphify rebuild
- **AND** it SHALL use the same marker-based pattern (`# gitnexus-hook-start` / `# gitnexus-hook-end`)
- **AND** it SHALL be idempotent (re-running install does not duplicate the section)

#### Scenario: Hook is resilient to missing CLI tools
- **WHEN** gitnexus CLI is not available on PATH
- **THEN** the gitnexus refresh section SHALL skip gracefully
- **AND** it SHALL print a one-line warning to stderr
- **AND** it SHALL exit 0 (never block commits)
- **AND** the graphify refresh SHALL still run independently

#### Scenario: Hook handles post-checkout branch switches
- **WHEN** a branch switch occurs (git checkout / git switch)
- **THEN** the post-checkout hook SHALL rebuild the graphify graph for the new branch
- **AND** it SHALL NOT run gitnexus refresh on checkout (only on commit)
