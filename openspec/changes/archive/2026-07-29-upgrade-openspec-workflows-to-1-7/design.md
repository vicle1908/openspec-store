## Context

See `proposal.md` for motivation and scope. The current workstation resolves
`@fission-ai/openspec@1.7.0`, which npm marks as `latest`; the package requires
Node.js `>=20.19.0`. The repository's global OpenSpec profile is `custom`, uses
`delivery: both`, and selects all twelve project-declared workflows.

The repository nevertheless contains 144 OpenSpec skills generated by 1.6.0:
132 across eleven generator-managed tool surfaces and twelve separately owned
canonical copies under `.agents/skills`. It also contains 190 generated files
with runtime-specific `AskUserQuestion` or `TodoWrite` references. Policy still
declares OpenSpec 1.6.0. Codex skills contain stale slash-command references and
archive guidance that launches sync through a background task before moving the
change. `.kimi/` exists while the 1.7 tool contract uses `.kimi-code/`. The
release workflow installs OpenSpec through an unpinned bootstrap, and the
normal verification workflow skips validation when the CLI is missing.

The exact repository-approved generator tool IDs are `antigravity`, `claude`,
`codex`, `cursor`, `factory`, `kilocode`, `kimi`, `kiro`, `oh-my-pi`,
`opencode`, and `pi`. The exact workflow IDs are `propose`, `explore`, `new`,
`continue`, `apply`, `update`, `ff`, `sync`, `archive`, `bulk-archive`,
`verify`, and `onboard`.

The following upstream sources were checked on 2026-07-29:

- OpenSpec 1.7.0 release and full changelog:
  `https://github.com/Fission-AI/OpenSpec/releases/tag/v1.7.0` and
  `https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md`
- Project configuration and operation guidance:
  `https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md`
- Tool-specific paths and invocation syntax:
  `https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md`
- npm metadata for version, engine constraint, dependencies, and package
  integrity via `npm view @fission-ai/openspec@1.7.0 ... --json`

No service transaction, API, event, persistence, ordering, or delivery contract
changes. This is a repository toolchain and governed-instruction migration.

## Goals / Non-Goals

**Goals:**

- Make version selection, generation, distribution, validation, and CI consume
  one exact OpenSpec release.
- Regenerate with the complete workflow profile while preserving tool-native
  syntax and non-OpenSpec files.
- Make archive/sync behavior fail closed and verifiably synchronous.
- Turn version, invocation, path, and manifest drift into focused diagnostics.
- Provide project-specific apply/archive advice through the supported 1.7
  runtime surface.

**Non-Goals:**

- Make a personal global OpenSpec configuration the durable source of truth.
- Adopt stores, references, worksets, a custom schema, or additional AI tools.
- Rewrite application code or claim deployment readiness.
- Make `openspec update` run automatically from hooks or unattended CI.
- Change the workstation package-maintenance implementation in this change.

## Decisions

### 1. Use nativeVersions.openspec as the single repository pin

`scripts/config/agent-skill-surfaces.json#nativeVersions.openspec` becomes the
canonical exact version. Local refresh support, manifest generation, tests,
and CI read this value rather than repeat a second floating constant. CI sets up
Node.js 22, which satisfies OpenSpec 1.7.0's `>=20.19.0` engine, installs
`@fission-ai/openspec@<pin>`, and asserts `openspec --version` before use.

The same policy file gains an `openspec` block containing the approved
`profile`, `delivery`, exact ordered `workflows`, exact eleven `tools`, managed
roots, the legacy Kimi managed root, and invocation invariants. The existing
`nativeVersions.openspec` field remains the only version value; the new block
references that policy rather than introducing another pin.

Alternatives rejected:

- `@latest`: convenient but makes identical commits validate with different
  binaries and caused the current CI/version split.
- A second version file or workflow-local environment value: creates another
  synchronization problem without improving ownership.
- The developer's global configuration: machine-local and unsuitable as a
  reviewed repository contract.

### 2. Wrap the official generator with a fail-closed repository orchestrator

A dedicated `scripts/openspec-surfaces.sh` command, backed by
`scripts/openspec_surface_policy.py`, owns OpenSpec-specific preflight,
snapshot, refresh, and verification. It composes with the existing generic
`scripts/agent-skills.sh` manifest support instead of extending generic skill
link rollback to tool-specific generated commands and workflows. Before
invoking `openspec update --force`, the orchestrator performs these checks:

1. Verify the approved pin and Node engine compatibility.
2. Refuse to proceed while
   `~/.local/state/go-microservices-workstation-tool-update/active.lock` exists or
   when two consecutive CLI version probes are inconsistent. The current lock
   is absent and the latest maintenance run succeeded; this remains a reusable
   precondition for future refreshes.
3. Verify the expected `custom` profile, `delivery: both`, and exact twelve
   workflows and eleven tools. It reads `openspec config list --json` but emits
   and retains only the redacted `profile`, `delivery`, and `workflows` fields
   because the raw global configuration includes a telemetry identifier. It
   reports the needed configuration correction but does not silently rewrite
   personal global settings.
4. Capture an inventory and rollback snapshot of OpenSpec-owned paths, policy,
   manifest, config, validators, and CI files.
5. Run the official generator once, then import the generated Codex skill set
   into `.agents/skills` as the repository's canonical shared copies and
   regenerate the manifest through existing repository support.

The upstream update loop can catch an individual tool failure, print it, and
continue with other tools. Therefore its exit status and summary are diagnostic
inputs only. The orchestrator accepts a refresh only after independently
verifying every expected tool, workflow, skill, command/prompt/workflow output,
version marker, invocation invariant, canonical copy, and manifest entry.

The wrapper does not install packages or edit global configuration. Dependency
installation remains explicit, and hooks never run an unbounded network fetch.

Alternative rejected: directly editing 144 skills and tool-specific commands.
The 132 tool copies declare generator ownership and would immediately drift
again; the twelve `.agents` copies must be synchronized from verified generated
sources rather than independently patched.

### 3. Preserve tool-specific outputs instead of normalizing all surfaces

The official 1.7 generator owns tool-adapter differences. Codex remains
skills-only and uses `$openspec-*`; Claude retains `/opsx:*`; filename-based
tools use `/opsx-*`; Kimi Code uses `/skill:openspec-*` under `.kimi-code/`.
Only the declared `.agents/skills` and `.codex/skills` shared pair remains
byte-identical under existing documentation policy. Other tool surfaces are
validated for version and adapter invariants, not byte equality.

OpenSpec 1.7 automatically performs the Kimi migration before generation. It
moves only managed `openspec-*` skills and `opsx-*` commands, preserves
hand-authored files in `.kimi/` and `.kimi-code/`, and retains/reports a
divergent destination copy instead of overwriting it. Repository logic verifies
that behavior and stops on unresolved ambiguity; it does not manually move the
whole directory.

`.agents/skills` is not an OpenSpec tool adapter and is never expected to be
created by `openspec update`. Repository synchronization copies the twelve
verified Codex skills there only after all eleven upstream-managed tool
surfaces pass validation.

### 4. Add operation guidance to project config, not generated files

`openspec/config.yaml` gains concise `operations.apply.guidance` and
`operations.archive.guidance` arrays. Apply guidance covers repository
instruction discovery, dirty-worktree preservation, focused checks, and task
completion evidence. Archive guidance covers explicit approval, implementation
verification, strict validation, main-spec sync/validation, retained evidence,
and bounded readiness claims.

These entries are advisory inputs fetched at execution time. Mandatory safety
and validation remain in `AGENTS.md`, specs, scripts, and CI; generated files
are not patched to embed local policy.

### 5. Validate version, syntax, paths, and archive safety separately

Extend the existing documentation/governance tooling and fixtures to check:

- approved pin equals generated metadata, policy, manifest, and CI install;
- the exact eleven tool surfaces contain all expected outputs for the twelve
  workflows, yielding 132 generator-managed skills before canonical sync;
- Codex has skills only and uses `$openspec-*` references;
- tool-specific commands use their registered invocation form;
- OpenSpec-owned `.kimi/` content has migrated to `.kimi-code/`;
- generated files no longer require Claude-only interaction/task tools;
- archive and bulk-archive guidance fetch current runtime inputs, runs sync
  inline, verifies main specs, and stops before move on failure;
- all upstream surfaces are complete even when the generator reports a partial
  per-tool failure and continues; and
- the twelve `.agents/skills` and `.codex/skills` OpenSpec pairs remain exact.

Tests use disposable fixtures and never regenerate the real workspace. The
real refresh stays an explicit reviewed action because its expected diff is
large and contains path migrations.

### 6. Make strict OpenSpec validation mandatory in both CI paths

The release-evidence and normal verification workflows share the canonical pin
and Node setup pattern. Neither checks `command -v` to decide whether validation
is optional. Installation failure, a mismatched version, or
`openspec validate --strict --all --no-interactive` failure blocks the job.
The validation result remains planning evidence; it does not establish service,
deployment, staging, or production readiness.

### 7. Keep stores and automatic self-upgrade disabled for this rollout

The nearest repository OpenSpec root is healthy and there are no registered
references needed for this scope. Store/default-store behavior remains beta and
per-machine. The repository also does not depend on the interactive 1.7
self-upgrade prompt; the wrapper requires the reviewed pin and uses
`OPENSPEC_NO_UPDATE_CHECK=1` for deterministic refresh checks where applicable.

### 8. Refresh retained deployment evidence before documentation acceptance

`make validate-documentation` compares a digest covering `Makefile`, `deploy`,
`scripts`, `tests`, and `openspec` with the manifest named by
`verification/documentation-currency.json#currentDeploymentManifest`. This
change necessarily modifies `scripts` and `openspec`, so its final documentation
gate cannot reuse the current retained manifest.

After all implementation changes and focused checks pass, run
`make validate-deployment`, retain the exact newly produced manifest, update
`currentDeploymentManifest` to that retained path, and only then run
`make validate-documentation`. This refresh establishes evidence compatibility
for the final source state; it does not establish cloud, staging, production,
or service deployment readiness.

## Risks / Trade-offs

- **Large generated diff obscures local changes** → Snapshot first, classify
  files by owner/tool/workflow, review deletions and path moves separately, and
  reject edits outside the allowlisted generated surfaces.
- **A future global npm maintenance run changes the executable during
  regeneration** → Gate on the updater lock and stable pre/post CLI version
  probes; do not terminate or compete with the updater.
- **Personal profile drifts from repository expectations** → Fail with exact
  remediation instead of silently changing global settings; record the profile
  in refresh evidence.
- **Tool adapter migration removes hand-authored content** → Determine ownership
  by generated file names/metadata, snapshot legacy paths, and stop on ambiguous
  files.
- **One policy JSON becomes a build input for CI** → Validate its schema and
  exact semver before installation; a malformed or missing value fails early.
- **Advisory operation guidance is mistaken for enforcement** → Keep mandatory
  rules in validation/specs and test that operation guidance remains separate
  from task state and artifact rules.
- **Rollback restores only part of the version set** → Define the rollback unit
  as pin, generated surfaces, canonical copies, manifest, config, validators,
  and CI together; rerun focused checks after restore.
- **Documentation validation uses evidence for an earlier source digest** →
  Generate and retain a new deployment-validation manifest for the final
  implementation state before updating the documentation evidence pointer.

## Migration Plan

1. Verify the workstation updater lock is absent, inspect its latest successful
   redacted report, and confirm stable `openspec --version` output.
2. Add the canonical version preflight, snapshot/inventory support, and fixture
   tests without regenerating the workspace.
3. Update the pin to 1.7.0, configure operation guidance, and prepare validator
   expectations for current tool paths and invocations.
4. Capture the managed-surface snapshot, run the official refresh once, verify
   the automatic ownership-aware Kimi migration and every generated tool
   output, import canonical shared skills, and refresh the manifest.
5. Review the diff by owner and tool; prove unrelated files and active OpenSpec
   changes are unchanged.
6. Pin both CI paths, remove optional validation behavior, and run focused
   fixture, guidance, affected-change, and repository-wide strict validation.
7. Run `make validate-deployment` for the final implementation state, retain the
   exact manifest, update `currentDeploymentManifest`, then run
   `make validate-documentation`.
8. Retain exact version/profile/surface/check evidence and hand off for
   implementation verification without broadening the evidence into a
   deployment-readiness claim.

Rollback restores the captured coherent OpenSpec-owned set and reruns focused
validation. If rollback returns to 1.6-generated files, the approved pin and CI
must return to the same reviewed version in the same operation.
