## Why

The current Jira sprint report is ticket-centric: rows are issues, columns are fields. Engineering leads have asked for a developer-centric view that shows per-person delivery throughput (merged MRs, deploys to dev, reopens, stale tickets, median / p90 cycle time) without losing the clickable per-ticket detail. The existing `Person Capacity` tab covers activity (worklogs) but not delivery — there is no place to answer "how many tickets did Alice ship to dev this week, and how long did they take?" without manually grepping Jira and GitLab.

## What Changes

- Add a new `Developer Performance` tab to the existing sprint-report spreadsheet (separate from the existing `Person Capacity` and `Sprint Report` tabs).
- Render one row per `(developer, ticket)` with the developer identity cells merged vertically across the developer's tickets and per-ticket metrics in the right-hand columns. Median / p90 cycle time and reopen / stale aggregates appear in a per-developer footer band, not per row.
- Join each ticket to its linked GitLab MRs (remote-link first, branch-name regex fallback) and capture `merged_at` plus the earliest deployment to `dev`.
- Compute per-developer aggregates: median + p90 cycle time (`In Progress` → first deploy to dev), median + p90 reopens per ticket, ticket counts (assigned / merged / deployed / stale).
- Stale-ticket detection per status, with thresholds configurable via env vars (`DEV_PERFORMANCE_STALE_*_DAYS`).
- Use a local SQLite diff cache (`~/.tdt/state/jira-daily-reports/dev_performance_cache.sqlite`) so hourly runs only emit changed rows to the Sheets API, keeping writes bounded.
- Use the existing `tdt_sheets.SheetsClient(ServiceAccountAuth.from_env())` write path (3-level credential fallback, mtime cache, token refresh) — no raw google-api-python-client code.
- Use the canonical schedule registration pattern: add `_CRON_DEV_PERFORMANCE` to `jira_daily_reports.dbos_scheduling`, register the workflow in `register_all_schedules`, and update `agent-core/deployments/scheduler/generators/jira.py` to emit the new entry in the generated `~/.tdt/schedules/jira-daily-reports.yaml` manifest.
- Use only existing client factories (`tdt_core.clients.jira.JiraClientFactory`, `tdt_core.clients.gitlab.GitlabClientFactory`). No new Python dependencies.

## Capabilities

### New Capabilities

- `developer-performance-tab`: Per-developer delivery reporting — joins Jira tickets to GitLab MRs / deployments, computes per-(developer, ticket) rows with merged developer identity and per-developer aggregate footer, writes a `Developer Performance` tab into the existing sprint-report spreadsheet, and uses a SQLite diff cache for incremental updates.

### Modified Capabilities

- None. The existing `jira-daily-reports`, `person-capacity-worklog-mode`, and `person-capacity-report` capabilities are additive-compatible: their tabs stay untouched, their run cadence stays untouched, and no existing requirement changes. New code calls into the shared `_jql_paginated` helper from `jira-daily-reports` rather than calling `jira.jql(...)` directly, which is already a requirement of that capability.
- The shared `jira-daily-reports/schedule.py` `SCHEDULES` dict adds one entry (`dev-performance`). The existing `test_all_13_crons_match_schedule_dict` test is updated to expect 14 entries.
- The `agent-core/deployments/scheduler/generators/jira.py` `_JIRA_CMDS` list adds one tuple `("dev-performance", "dev-performance")`. The generator pattern already supports this addition without any other change.
- `jira-daily-reports/tests/test_dbos_scheduling.py` `TestScheduleCount` expects 14 entries today (the class docstring mentions 15 but the test list has 14). The expected list is updated to include `"jira-dev-performance"`.

## Impact

- `jira-daily-reports`:
  - New module `src/jira_daily_reports/dev_performance/` with submodules `cli.py`, `source.py`, `join.py`, `metrics.py`, `row_builder.py`, `summary_builder.py`, `sheet_writer.py`, `diff_cache.py`, `stale_thresholds.py`
  - New CLI subcommand `dev-performance` registered in `src/jira_daily_reports/cli.py`
  - New entry in `src/jira_daily_reports/schedule.py` `SCHEDULES` dict
  - New `_CRON_DEV_PERFORMANCE` constant + registration in `src/jira_daily_reports/dbos_scheduling.py`
  - Updated `tests/test_dbos_scheduling.py` schedule count assertions
  - New tests directory `tests/dev_performance/` and integration tests
- `agent-core`:
  - Updated `deployments/scheduler/generators/jira.py` `_JIRA_CMDS` tuple list to include `("dev-performance", "dev-performance")`
- `~/.tdt/schedules/jira-daily-reports.yaml`: regenerated manifest (auto-generated by `agent-core/deployments/scheduler/generators/jira.py`; same deploy pipeline as existing entries)
- `~/.tdt/.env`: new optional env vars with safe defaults (`DEV_PERFORMANCE_*`). `.env.example` does not need updates because defaults work out of the box.
- Google Sheets workbook layout: adds one new tab `Developer Performance`. Does not modify `Sprint Report` or `Person Capacity`. The new tab's gid is persisted via the `SHEET_LINKS` env var (same pattern as `jira-catalog-tab`).
- `jira-skill` and the `ticket-intelligence-core` / `CapacitySignal` Pydantic model: not touched. Out of scope.
- Mobile apps (`poems-mobile3-ios`, `poems-mobile3-android`): not impacted.
- `webhook-receiver`, `ai-review`, `tdt-core`, `tdt-sheets`: not impacted.

## Non-Goals

- Replacing or modifying the existing `Person Capacity` (worklog-mode) tab or the `Sprint Report` tab.
- Adding deploy-to-staging or deploy-to-production columns (only `dev` is in scope per the request).
- Wiring into `jira-skill`'s `CapacitySignal` Pydantic model.
- Building a real-time webhook-based cache (deferred; this change uses a 2-hour polling cadence).
- Modifying any Android/iOS code, or any Python code outside `jira-daily-reports` and `agent-core/deployments/scheduler/generators/jira.py`.
- Adding new methods to `tdt_sheets`; the existing `SheetsClient.batch_update()` already supports the `mergeCells` request body.
- Adding a separate scheduling subsystem; this change reuses the existing DBOS scheduler and `_CRON_*` constant pattern.
